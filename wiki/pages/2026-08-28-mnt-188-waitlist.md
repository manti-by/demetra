# MNT-188: Waitlist

## TL;DR

The waitlist lets blocked users register interest; admins approve entries via CLI to add them to the allowlist. The service includes a `waitlist_entries` table, HTTP 202 waitlist responses in the auth flows, React waitlist UI states, and CLI management commands.

---

## Overview

The waitlist service is implemented in `demetra/services/auth/waitlist.py` and includes a join API, approval flow, notification, and audit. The `waitlist_entries` table is added via an Alembic migration, and the existing auth flow is updated to surface the new 202 waitlist path. The implementation also includes CLI management commands and tests to verify the implementation.

## Implementation Plan

### Overview

The implementation plan involves adding a waitlist service to handle blocked users, creating a new DB table for waitlist entries, and wiring the waitlist into the existing auth flow.

### Key Design Decisions

1. **Waitlist table schema**: The waitlist table will have columns for `id`, `entry_type` (email/github_username), `value` (normalized), `status` (pending/approved/rejected/joined), `note`, `created_at`, `approved_at`, `approved_by`, `joined_at`, `notified_at`. A unique constraint on `(entry_type, value)` will prevent duplicates.

2. **Service module**: A new service module `demetra/services/auth/waitlist.py` will be created to handle waitlist operations, including joining, approving, listing, and removing waitlist entries.
